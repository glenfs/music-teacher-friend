MusicEd is a technically ambitious music education app with substantial breadth: eight training modes, twenty-two learning modules, procedural exercise generation (Hanon / Czerny / Scales), and a thoughtful product layer for per-student data and a teacher dashboard. The ear-training and sight-reading gameplay loop is genuinely strong; the procedural exercise generator is a real competitive moat.

However, the product today is best described as "a practice app with a teacher dashboard attached, not yet a studio tool." Five gaps stand between MusicEd and a viable paid teacher product:

  1. Cloud sync is unfinished — multi-device teachers will lose data.
  2. Teachers can't see what students actually practiced — the data exists in module_progress.json but is never surfaced in the dashboard.
  3. Assignments don't reach students — TeacherStore.add_assignment() works, but there is no student-side queue UI.
  4. No curriculum alignment — no link from exercises to ABRSM / RCM / Faber method books.
  5. 33K-line monolith in scripts/interval_birds.gd makes every change risky and onboarding nearly impossible.

2. Gameplay & Feature Completeness

What's strong

  • Eight training modes with configurable difficulty (Interval, Chord, Sight Notes / Chords / Grand Staff, Rhythm Flow, Note Chase, Progression, Scale/Mode, Cadence). Rare breadth for a consumer app.
  • 22-module learning curriculum with gated progression, 1–3 star mastery, review queue (spaced repetition), and hands-on exercises tied to notation concepts.
  • Procedural exercise generation (Phases 1–8 live): Hanon, Czerny, scales, arpeggios, 5-finger drills with difficulty estimation. Competitors don't have this.
  • Per-student data architecture: user://students/<id>/ routing, ActiveStudent selector, LessonSession tracking, legacy-migration path. Well-designed, though currently underutilized.
  • Audio engine via Conductor avoids drift from get_tree().create_timer() — gives accurate musical timing.

Critical gaps

2.1 Sight singing is incomplete

scripts/sight_singing/sight_singing_session.gd handles note-by-note evaluation, but singing_evaluator.gd and phrase_analyzer.gd are minimal. The custom sight_singing_staff.gd Control is documented as "no longer used" — suggesting an incomplete refactor. Playable, but phrase/legato scoring is missing.

2.2 No assignment system end-to-end

TeacherStore.add_assignment() / mark_assignment_done() exist (~lines 451–527), but there is no UI to create assignments and no student-side queue showing "Today's assignments". The data plumbing is half-done.

2.3 No grading or feedback loop

Teacher can log "Sarah practiced scales," but the dashboard does not surface:

  • What modules Sarah actually completed (per-student progress JSON exists but isn't rendered).
  • Her accuracy trends across sessions.
  • Weak intervals / notes. ProgressStore.compute_missed_ids() and TeacherStore.get_weak_items() are both implemented but never called from the teacher flow.

2.4 Missing teacher-workflow features

  • Attendance tracking — no way to mark "Sarah missed lesson."
  • Practice time metrics — no "Sarah practiced 45 min this week" rollup.
  • Parent dashboard / shareable reports — no PDF export, no parent link.
  • Recital planning — no event/performance tracking.
  • Billing — no invoice, lesson rate, or subscription management.
  • Curriculum alignment — no link between exercises and ABRSM / RCM / Faber method books.

3. UI / UX Analysis

Home menu

Two flows — Practice and Learn — render through HomeMenuState + HomeMenuUI + HomeFlowController. Decoupled state from rendering is good. But:

  • No visual hierarchy. Eight modes are presented at roughly equal weight. A new student doesn't know where to start. The "Quick Practice" button helps, but the menu still feels like a control panel rather than a path.
  • Settings panel proliferation. Each mode opens its own settings (chord tiers, interval choices, BPM, etc.). The chord tier accordion alone has 22 chord types in 4 collapsible groups. For a student/teacher in a 30-min lesson, this is friction.
  • Theme selector hidden per memory note. Good for MVP, but indicates the UI is carrying dead controls that should be deleted, not hidden.

Teacher dashboard

Five tabs (Overview, Repertoire, Lesson Log, Assignments, Technique) built procedurally in teacher_dashboard.gd (~1,500 lines of _build_* methods).

Visibility issue: The dashboard is the most important surface for paid adoption, and the most underbuilt screen.
  • Overview tab is sparse — student list + a few summary fields. No "what did this student practice this week?" card. No weak-area surfacing. No streak/attendance signal.
  • Lesson log sort order is wrong: entries are insert(0, ...) — backdated entries appear out of order. Audit doc item #1 flags this; still unfixed.
  • No live refresh: _module_progress_stats is passed in at setup and never updated — teacher sees a static snapshot.
  • No search or filter on lesson logs: past ~20 entries becomes unmanageable.
  • No undo on delete: lesson logs and assignments deleted with one click. Risky for a teacher's data.

In-session HUD & result screen

  • Practice-mode HUD distinction (teal/blue background) and streak toasts are good polish.
  • Result screen bounce animation + dynamic motivational title is a nice touch.
  • Result screen is text-heavy. Time / accuracy / miss summary / focus tip are all stacked text. A small chart (accuracy line, miss count bar) would communicate more in less space.
  • No "share to teacher" action from the result screen. The natural moment for a student to send progress to their teacher is right after finishing a session.

Sight reading & grand staff

  • Grand staff (treble + bass) for sight chords is well-implemented with realistic voicing constraints.
  • Hardcoded absolute X/Y positioning (STAFF_LEFT_X := 56.0, etc.) — on a small phone profile the staff can clip. DeviceProfileResolver isn't applied to staff layout.
  • Z-order strategy is fragile: hardcoded z_index values (0/10/20/50). One incorrect add_child() could bury content. Worth replacing with named CanvasLayer groups.

Onboarding

  • First-run auto-launches Quick Practice (beginner intervals) — excellent zero-friction start.
  • Per-mode onboarding overlays (ear intro, note chase intro) with "How to Play" replay button.
  • No teacher onboarding. A teacher opening the app for the first time gets dropped into the student experience. There's no "I'm a teacher → set up your studio" path.
  • No empty-state UI in the teacher dashboard. New teachers see blank tabs with no prompts.

Learning map

  • Compact overview card consolidating pace + heatmap + review CTA is a good design.
  • Pace controls (Guided / Normal / Quick) respected by lesson player.
  • 18-module map in one scrollable view is a lot. Grouping into chapters or seasons (e.g. "Reading Basics", "Intervals & Chords", "Capstone") would help orientation.

The 33K-line monolith

scripts/interval_birds.gd contains mode constants, gameplay state, UI setup, audio orchestration, settings persistence, teacher integration, learning routing, and QA hooks — all in one file. Costs:

  • Bug fixes anywhere touch unrelated concerns.
  • New contributors cannot orient.
  • Merge conflicts are guaranteed for any team.
  • Hidden coupling: instance vars like _practice_mode_enabled and _focus_missed_ids are read from a dozen handlers.

Suggested extraction:

  • GameplayStateMachine — mode transitions, scoring, lives, streak.
  • GameplayUIController — HUD, result box, status label.
  • GameplayAudioController — prompt playback, feedback, replay.
  • TeacherIntegration — student tracking, weak-item recording.
  • Per-mode controllers: IntervalMode, ChordMode, SightMode, etc.

Save/load robustness

  • TeacherStore backs up files before overwrite; corrupt files moved to .corrupt.<timestamp>.
  • JSON parsing uses typeof() guards.
  • Session tokens prevent race conditions in the quiz loop.
  • No streaming for large rosters — everything in memory.
  • FileAccess.open() failures are silent — teacher loses data with no toast / warning.
  • No conflict detection for multi-device edits (planned in Tier 3 cloud sync).

Audio assets

88 piano MP3 samples loaded at startup. Estimated 10–15 MB resident memory. Mitigations to consider for mobile:

  • Load only the octave range in current use.
  • Stream less-frequent samples (sub-C3, super-C6).
  • Add a per-session audio warm-up step rather than full preload.

Testing

qa_run.ps1 runs qa_runner.gd — an integration-level bot, not unit tests. There are no tests for:

  • Stat computation (compute_missed_ids, get_weak_items).
  • Date sorting in lesson logs.
  • JSON migration between schema versions.
  • Exercise generator output validity (the self_test helpers exist but aren't part of CI).

The five intermittent QA failures noted in memory (Ear 5/6, Progression smoke, Scale/Mode smoke, Note Chase) suggest the QA bot has timing flakiness — worth fixing before shipping so a CI green light is meaningful.

6. Path to "Pro & 1K Customers"

Tier 1 — Make teachers stick (Months 1–3)

  1. Finish cloud sync. Supabase skeleton already in scripts/sync/. Finish OAuth, snapshot push/pull, conflict resolution. Teachers use tablet in studio + laptop at home; without sync, the roster fragments and they churn.
  2. Surface practice data in the dashboard Overview. Call ProgressStore.compute_missed_ids() and TeacherStore.get_weak_items(). Render a "Since last lesson" card per student: time practiced, modules completed, weak intervals. This is the biggest pedagogical ROI in the codebase — the data exists, it's just hidden.
  3. Assignment → student pipeline. Build a "Create assignment" UI in the Assignments tab. Add "Today's Assignments" section to the student home menu. Mark complete on session end.
  4. Polish or descope sight singing. Either finish phrase scoring or hide the mode until v2.

Tier 2 — Differentiate (Months 4–6)

  1. Curriculum alignment. Add data/curriculum_mapping.json linking exercises to ABRSM / RCM / Faber. Search the exercise library by method book.
  2. Parent dashboard / exportable PDF reports. Monthly summary: accuracy trends, pieces completed, weak areas. Use existing LearningProgress + TeacherStore session history.
  3. Lesson scheduling. Calendar with recurring slots, attendance marking, auto-drafted lesson log template.
  4. Empty-state & teacher onboarding. First-run teacher path: "I'm a teacher" → create studio → add first student → assign first exercise.

Tier 3 — Studio governance (Months 7+)

  1. Multi-teacher support. teacher_id in TeacherStore schema; per-teacher assignment history; PIN gate on dashboard.
  2. Billing integration. Stripe / RevenueCat — lesson rate, attendance-driven invoices, subscription tiers.
  3. Teacher composer UI. Let teachers build custom drills from the procedural generator — turns the moat into a teacher-facing feature.
  4. Recital / event mode. Performance tracking, student showcase, video/audio recording integration.

8. Suggested 12-Week Roadmap

Weeks 1–4 — Foundation

  • Cloud sync finished (Supabase).
  • Practice data in Overview tab.
  • Lesson log sort + search + undo.
  • Decision on sight singing (polish or descope).

Weeks 5–8 — Teacher value

  • Assignment → student pipeline shipped.
  • Teacher first-run onboarding.
  • Curriculum metadata + library filter.
  • PDF report export (v1).

Weeks 9–10 — Health

  • Extract gameplay state machine from interval_birds.gd.
  • Extract mode controllers (interval / chord / sight).
  • Add unit tests for stats + migrations.

Weeks 11–12 — Launch prep

  • Payment integration (Stripe / RevenueCat).
  • Landing page, pricing, trial flow.
  • Beta cohort of 20 teachers; iterate on dashboard.
  • Marketing copy aligned to "studio tool, not a game".

Closing

The hard part — building a fun, musically credible practice engine with 8 modes, 22 modules, and procedural exercise generation — is done. The remaining work is mostly connecting what already exists: surfacing student progress to teachers, syncing data between devices, and routing assignments back to students. Those connections, plus the monolith refactor and a basic payment flow, take MusicEd from "interesting educational app" to "viable teacher tool."

The moat (procedural exercises, multi-mode breadth, learning curriculum) is real. The biggest risk is shipping the product in its current half-connected state, where teachers see the dashboard, fail to find their student's practice data, and conclude the app is "just another practice game." Prioritize the visibility work before any marketing push.
