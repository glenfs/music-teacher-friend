What you already have working in your favor

  • Per-user identity — Supabase auth via email + OTP. The single most important piece of paid software: a stable account that survives across devices.
  • Cross-device state — Cloud Sync Tier A shipped this week. Subscription status will sync the same way.
  • Per-user table with Row Level Security — proven pattern (the sync_snapshots table). A subscriptions table copies the same shape.
  • IS_TEACHER_EDITION flag already exists — the codebase already separates Teacher Edition from Student Edition. Adding an is_pro_subscribed() check beside it is small.
  • Bundled deliverable already present — students, lessons, progress are already organized into per-student folders. Teachers paying for "all my students backed up + reports" is a natural value proposition.

The three strategic decisions

Decision 1

Business model

ModelProsConsFit for this app
Subscription ($/mo or $/yr) Recurring revenue funds cloud sync + new content. Industry-standard for SaaS teaching tools. Higher friction. Some teachers resist. Best fit. Cloud sync = ongoing server cost = subscription is honest.
One-time purchase Low friction, "own it" psychology. No recurring revenue. Can't fund ongoing cloud sync long-term. Works as a "Lifetime" tier alongside subscriptions ($299).
Freemium Wide top-of-funnel, low-risk for the teacher. Conversion typically 2–5%. Combine with subscription. Best results.
Per-student pricing Scales with the studio. Adds complexity; harder to communicate. Defer until you have data on studio sizes.
★ My pick: Freemium → subscription. Free tier with 1–2 students + core practice features; Pro tier ($9.99/mo or $99/yr) unlocks unlimited students, cloud sync, auto reports, recital prep, etc. Add a Studio tier ($19.99/mo) later for multi-teacher.

Decision 3

Distribution channel — platform constraints matter

Technical architecture

New Supabase table: subscriptions

create table public.subscriptions (
  user_id              uuid primary key references auth.users(id) on delete cascade,
  status               text not null,   -- 'trial' | 'active' | 'past_due' | 'cancelled' | 'expired'
  plan                 text,            -- 'monthly' | 'annual' | 'studio' | 'lifetime'
  current_period_end   timestamptz,     -- when access expires
  trial_ends_at        timestamptz,     -- 14-day trial window
  stripe_customer_id   text,
  stripe_subscription_id text,
  provider             text,            -- 'stripe' | 'google_play' | 'app_store'
  created_at           timestamptz default now(),
  updated_at           timestamptz default now()
);

-- RLS: users read only their own row.
alter table public.subscriptions enable row level security;
create policy "read own subscription"
  on public.subscriptions for select
  using (auth.uid() = user_id);
-- Writes only via service role (webhook). No client-side write policy.

Three components in the Godot app

  • scripts/billing/subscription_service.gd — reads the subscription row, exposes is_pro(), trial_days_left(), expires_at(). Cached locally for offline use.
  • scripts/billing/paywall_dialog.gd — shown when a gated feature is accessed without Pro. Lists the value prop + "Start free trial" / "Subscribe" buttons.
  • Platform adapters — stripe_checkout_launcher.gd (opens browser to Stripe Checkout), later google_play_billing.gd for Android, app_store_iap.gd for iOS.

One server piece (outside Godot)

A tiny webhook receiver — one Supabase Edge Function in TypeScript, ~50 lines — that:

  1. Receives Stripe webhook events: checkout.session.completed, customer.subscription.updated, customer.subscription.deleted.
  2. Updates the subscriptions table accordingly.

That's literally all the server-side code you need.

The flow end-to-end

Desktop subscription:

  1. Teacher hits a Pro feature → paywall dialog → "Subscribe $9.99 / mo".
  2. App calls OS.shell_open("https://yourapp.com/subscribe?user_id=<id>").
  3. Browser opens Stripe Checkout. Teacher pays.
  4. Stripe webhook fires → updates Supabase subscriptions.status = 'active'.
  5. App polls the subscription row (every 30s while paywall is open, then on launch) → sees active → unlocks features.

Android subscription (later):

  1. Same paywall, but the "Subscribe" button uses Google Play Billing (Godot plugin).
  2. Play Billing returns a purchase token.
  3. App sends token to your server → server validates with Google's API → updates Supabase.
  4. App polls subscription row → unlocked.

Phased rollout

Phase A · ~1 week Pre-launch: desktop end-to-end paid
  1. subscriptions table + RLS in Supabase. ~30 min.
  2. subscription_service.gd reading the row + caching locally. ~2 days.
  3. Paywall dialog visual + copy. ~1 day.
  4. Stripe account setup, products + prices in Stripe dashboard. ~2 hrs.
  5. Stripe webhook Edge Function → updates Supabase. ~2 hrs.
  6. Subscribe button → Stripe Checkout flow. ~1 day.
  7. Free-trial logic: first sign-in starts a 14-day trial automatically. ~half day.
  8. Gate the features listed in the Free-vs-Pro table with subscription_service.is_pro() checks. ~1 day.
Total: about a week of focused work. You can launch paid on desktop end-to-end with just this.
Phase B · ~1 week Android (when you publish to Play Store)
  1. Register subscription products in Google Play Console.
  2. Add godot-google-play-billing plugin.
  3. Server-side validation of Play purchase tokens.
  4. Hook into the same paywall — different button label on Android.
Phase C · ~1 week iOS App Store (only if you go iOS)
  1. Same shape as Android but with StoreKit.
  2. Required: Apple Sign In if any social sign-in is offered.
Phase D · later Maturity — when you have real subscriber data
  1. Annual plan with discount (already in pricing).
  2. Studio tier (multi-teacher).
  3. Lifetime tier ($299).
  4. Promo codes (music teacher conferences, beta-tester rewards).
  5. Referral discounts.
  6. Team / multi-teacher billing.

Gotchas: legal, operational, conversion

Legal

  • Terms of Service — subscription terms, cancellation policy, refund policy.
  • Privacy Policy — student data is minor data: COPPA/FERPA implications for US, GDPR-K for EU. The privacy notice from the cloud-sync plan covers most of this.
  • EU cancellation rights — cancellation must be as easy as subscription, no friction allowed.
  • Data export rights — users can request all their data. You already have the bundle code from sync.

Operational

  • Refunds — handled automatically by Stripe webhooks. Your code just demotes status.
  • Payment failures — 3–7 day grace period before locking features is standard.
  • Family sharing — Apple's Family Sharing for iOS subscriptions. Plan for it.
  • Tax (VAT, GST, sales tax) — use Stripe Tax OR switch to Paddle / Lemon Squeezy (they're "merchant of record" — they handle all tax for you in exchange for slightly higher fees ~5–6%). For an indie shipping internationally, MoR is worth every penny.

Conversion

  • First-run = trial, never gate at sign-up. Show value before asking for money.
  • No credit card required for trial. Lowest possible friction.
  • Days-left counter visible during trial (subtle, in the corner).
  • At trial end: dialog with "your data stays for 90 days while you decide" reassurance.
  • Cancellation flow: ask why, offer 50% discount once, let them leave easily.

★ My one-thing-first recommendation

If you do exactly ONE thing before everything else:

Set up the subscriptions table + a 14-day free trial that starts on first sign-in, with no paywall yet.

That gives you:

  • Server-side per-user subscription state (the architectural piece).
  • Trial counter visible in the app.
  • Data on how many teachers actually use the app for 14+ days (your activation funnel).
  • Zero risk — nothing gets gated yet.

Then you can ship paywalls + Stripe + paid Pro tier as a follow-up, with the knowledge of who's a real candidate vs. who churned.
