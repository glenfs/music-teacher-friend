The three decisions that shape everything else

Three forks where the answer changes the architecture. Smaller choices can be made as we go.

Decision 1

Backend choice

OptionProsCons
Supabase Postgres + auth + storage in one. Free tier covers thousands of teachers. REST + JS SDK callable from Godot via HTTPRequest. Built-in Google / email / magic-link sign-in. Row-Level Security for per-teacher data isolation. Self-hostable escape hatch. One more vendor to depend on.
Google Drive (per-user) Free for users (their own Drive quota). No backend to maintain. Teacher's Google account = their data. File-based; awkward for queries and multi-device conflict resolution. Each teacher needs Google. Mobile OAuth flow is fiddly. Fights everything you'll want later (parent portal, real-time, analytics).
Firebase Mature, Google-owned, real-time DB built in. NoSQL forces denormalization for the relational data shape you have. Pricing gets steep at scale. Less ergonomic than Supabase for this app.
Custom backend (Node/Go on Render/Fly.io) Total control. Now maintaining a server + DB + auth + backups. Big distraction from teaching features.
PocketBase (self-hosted single binary) One binary, SQLite-backed, auth built in, very cheap to host. Minimum vendor lock-in. Smaller community, you operate it yourself.
★ My pick: Supabase. Best fit for a solo dev shipping a relational-data app to teachers + students. Second choice if you want to avoid vendor risk: PocketBase.
Decision 2

Sign-in model

OptionWhen it fits
Google OAuth Fastest UX, no passwords to forget. Required for "Sign in with Google" surfaces.
Email + password Works without OAuth setup. Universally familiar.
Magic link (passwordless) One-tap email link → signed in. Lovely UX. Supabase supports natively.
Apple Sign In Required by the App Store if you ever publish on iOS and offer any other social sign-in.
★ My pick for MVP: Email + password AND magic link (Supabase gives both for free). Add Google + Apple in a follow-up. Keeps the launch path simple.
Decision 3

MVP scope — how ambitious for v1?

TierWhat it doesEffort
A — Backup / Restore Teacher signs in, presses Sync, app pushes a snapshot bundle to cloud. On a second device, signs in → pulls down the snapshot. "Import/export over cloud" — covers the exact use case that motivated removing the file-based import/export. Small (~1–2 weeks)
B — Per-record sync Each student / lesson-log / progress entry tracked individually. Last-write-wins per record on conflict. Multi-device "feels" continuous. Medium
C — Real-time multi-device Live updates across devices (teacher's tablet shows student's home practice within seconds). WebSocket subscriptions. Larger
★ My pick: Ship Tier A first. Get teachers using it for real backup. Evolve to Tier B once usage patterns are clear. Tier C is a phase-3 goal.

  2. A Supabase project (free): sign up at supabase.com, create a project, share the Project URL + anon (public) API key. I never need the service-role key — that stays with you. ~5 minutes to set up.
  3. Sign-in model for MVP — email/password + magic link recommended. Confirm or override.
  4. MVP scope — confirm Tier A (backup/restore) or pick another.

Things I do not need yet

  • Pricing tier on Supabase (free is fine until usage actually grows).
  • Student-facing auth model (Tier A doesn't touch this — teacher account owns all student data).
  • Exact schema (I'll propose one).
  • Apple / Google OAuth setup (later).

Privacy & student-data notes

Students are minors — even at MVP scale this matters

  • Data we sync is education-related, not PII-heavy (no addresses, no payment info), but it does include student names.
  • Recommended at first sign-in: a small privacy notice — "Your students' practice data syncs to your private cloud storage. Only you have access."
  • Delete-account path that wipes server-side data. Supabase RLS makes "only you have access" enforceable at the DB level.
  • COPPA only kicks in for direct-to-child services. Teacher Edition is teacher-facing, so the legal surface is small — but build the delete + privacy notice anyway; it's table stakes.

Offline-first behavior

App must keep working with no network. Sync is best-effort: queue writes, retry on reconnect, last-write-wins on conflict. The existing per-student JSON files become the source of truth locally; cloud is a synced shadow, never the source of truth at the device.

Network in Godot: Godot 4.6's HTTPRequest handles all the REST calls cleanly. No external dependency, no plugin needed.

Proposed Tier A architecture

A new SyncProvider module

Two files under a new scripts/sync/ folder:

  • sync_provider.gd — the interface (so the backend is swappable later).
  • supabase_sync_provider.gd — the implementation against Supabase REST.
SyncProvider:
  sign_in(email, password|magic_link)  → user_id or error
  sign_out()
  push_snapshot()         # bundle everything, upload as one row per device
  pull_snapshot()         # download latest snapshot, replace local files
  list_devices()          # for "you have 3 devices syncing"
  delete_account()        # GDPR / COPPA right-to-erase

One Supabase table to start: sync_snapshots

  • id, user_id, device_label, created_at, payload_json (the entire bundle).
  • RLS policy: user_id = auth.uid() — a teacher can only read/write their own rows.

UI in dashboard sidebar

  • Sign-in / sign-out controls.
  • "Sync Now" button (manual for Tier A).
  • "Last synced: 12 min ago" status text.
  • "Restore from cloud" with confirmation (replaces local — destructive, so guarded).

Existing architecture wins to lean on

  • scripts/students/active_student.gd already routes data per student.
  • Per-student folders at user://students/<id>/ — the natural unit to bundle.
  • pre_launch_deferred.md item #2 (removed export/import) tells me what NOT to bring back as file-based.
  • The _save_* and _load_* functions in interval_birds.gd are where local writes happen; the sync layer hooks just below those.

Once Tier A is in production for a few weeks and real failure modes surface, evolve into Tier B (per-record sync with last-write-wins).
