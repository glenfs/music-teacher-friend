Hearing Chords 🎹🐔

How Clefira learned to recognise every note a student plays — not just one.

Plain-language engineering doc · ML note detection

This document explains, in everyday terms, a feature we built: letting a student play a whole chord on their piano and have the app check every note they played. It covers the problem, the options we weighed, the one we chose, and what it took to ship it on both Windows and Android.

1The problem

Clefira can listen through the microphone and tell what note you sing or play. The original listener used a classic algorithm called YIN. YIN is excellent at one thing and one thing only: hearing a single note at a time.

But a piano is polyphonic — you can press several keys at once. When a student played a chord, YIN didn't politely fail. It picked one pitch out of the blur and reported it confidently. Worse, it sometimes reported a note that wasn't even played — a "phantom" pitch that a chord can create. So:

The bug the user reported: "When a note is shown I play a chord on my piano, it says I'm right — but I may not have played that note at all." A chord was sneaking past as a correct single answer.

The root cause isn't a coding mistake — it's a mismatch of tool to task. Asking a one-note detector to judge a chord is like asking someone to read out a single word from five people talking at once. They'll say a word, but you can't trust it.

2A 60-second primer: one note vs. many

Think of sound as a stack of pure tones. A single piano note is actually a "family" of evenly-spaced tones (the fundamental plus its harmonics). A chord is several of those families layered together.

  • Monophonic detection (YIN, CREPE): finds the one repeating pattern in the sound. Fast, accurate — for one note. Blind to chords.
  • Polyphonic detection (the hard problem): pulls all the simultaneous notes apart. This is what every "play-along piano app" needs, and it's genuinely difficult.
  • MIDI: not detection at all — the keyboard sends the exact notes over a cable. Always perfect, but needs a digital keyboard plugged in.

3The options we had

We looked at how the big commercial apps (Simply Piano, Yousician, flowkey) solve this, then mapped our realistic choices:

What the pros do: Simply Piano's own engineers say "common signal-processing algorithms are not enough" and use deep learning for the microphone. Every one of them also recommends MIDI for perfect accuracy. So our two-track answer — ML for the mic, MIDI for the cable — mirrors the industry.

4What we chose — and why

We chose to integrate Spotify Basic Pitch, an open-source neural network for turning audio into notes.

Why this model
  • It's free & commercial-safe — Apache-2.0 licence, including the model itself.
  • It's tiny — the model file is just 230 KB.
  • It's genuinely polyphonic — returns every note, across instruments.
  • It's proven — competitive accuracy from a small, fast network.
Why not the others
  • Training our own: huge cost to rebuild what Basic Pitch already gives us.
  • Classic DSP: more brittle, lower accuracy, still a lot of code.
  • MIDI-only: great, but excludes acoustic-piano students with no cable.

Before committing, we tested it on Clefira's own piano sound (we built test chords from the app's actual piano samples). It recovered the notes essentially perfectly — see Results.

5A key sub-decision: ONNX, not TensorFlow

The model can run under different "engines." The default for desktop experiments is TensorFlow — but you can't ship TensorFlow inside a game:

TensorFlowONNX Runtime chosen
Size on disk~300–500 MB~15 MB
Runs inside Godot?No plug-in existsYes
Speed per chord (desktop)~1,800 ms~64–120 ms
AccuracyIdentical — it's the same trained model, just a different engine running it.

So ONNX gives us the same answers, ~28× faster, in a package small enough to put in an app. That's the version we ship on both Windows and Android.

6What deploying it involved

We rolled it out in careful, verifiable stages — each one proven before moving on, so we never built on an unproven assumption.

  1. Prove the idea (Python) Ran Basic Pitch on chords built from Clefira's piano. It found every note — the concept was sound, so it was worth continuing.
  2. Confirm the shippable engine (ONNX) Re-ran with the lightweight ONNX engine to confirm it stayed accurate and got dramatically faster. This is the version that can actually go in the app.
  3. Prove it runs in native code Got ONNX Runtime running the model in C++ and confirmed the output matched Python exactly — the foundation everything else sits on.
  4. Port the "notes from numbers" logic The model outputs raw probabilities; turning those into clean note events is ~200 lines of logic. We re-wrote it in C++ and checked it against the original, note-for-note.
  5. Wrap it as a Godot add-on Packaged it as a PolyphonyDetector the game can call from one line of script, and verified inside Godot that raw audio in → correct notes out.
  6. Build for Android Recompiled the same C++ for phones (arm64) against the Android version of ONNX Runtime, producing a ready-to-bundle library.
  7. Wire it into a lesson Added a "🎤 Play it" button to Sight Reading Chords: the student plays the displayed chord, and the app reports which notes were right, missing, or extra.
One codebase, two platforms. The clever part of the final design is that Windows and Android run the exact same C++ — only the engine library underneath differs. Less code to maintain, and no chance of the two platforms drifting apart.

7How it works today

When a student taps "Play it" and plays a chord, this happens in about a tenth of a second:

🎤 Record a few seconds→ Tidy the audio→ 🧠 Basic Pitch (ONNX)→ Extract the notes→ Remove duplicates→ ✅ Compare to the chord

The student then sees feedback like "✓ Yes! You played every note," or "Close — missing C♯; extra G." Behind the scenes this is the new ChordDetection helper calling the native detector; if the detector isn't available on a given build, the button simply doesn't appear and nothing breaks.

9Surprises & gotchas

  • The model eats raw audio. We expected to feed it a "picture" of the sound (a spectrogram); it turns out that step is built into the model, which made our job simpler.
  • A hidden precision trap. One sub-step secretly used 64-bit maths; copying it in 32-bit shifted a note's boundary by a hair. We caught it only because we compared results exactly, not "close enough."
  • Windows vs. Android string types. The engine wants file paths in different formats on each OS — a one-line fix, but it broke the first Android build until spotted.
  • MIDI remains king. Even after all this, plugging in a digital keyboard is still the most accurate path — exactly what the commercial apps say. The ML mic path is for students without a cable.

10What's left

  • On-device check: the Android library is built and bundled, but running it on a real phone/emulator is the final confirmation step.
  • Polish: tune the listening window and feedback wording from real-classroom testing.
  • Reuse: the same ChordDetection helper can later power Chord Explorer and Practice Drills, not just Sight Reading Chords.
